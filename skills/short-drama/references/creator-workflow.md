# Creator-first 工作流

## 唯一落盘

每集按需维护五份创作者可读 Markdown：

| 阶段 | owner | 文件 |
|---|---|---|
| 剧本 | `short-drama-write` | `剧集/<EP>/剧本.md` |
| 视觉资产 | `short-drama-assets` | `剧集/<EP>/视觉设定.md` |
| 分镜与冻结关键帧 | `short-drama-storyboard` | `剧集/<EP>/分镜.md` |
| 图片提示词 | `short-drama-image-prompts` | `剧集/<EP>/图片提示词.md` |
| 视频提示词 | `short-drama-video-prompts` | `剧集/<EP>/视频提示词.md` |

没有内容时不预建空文件。一个请求只创建它实际需要的文档；从剧本、视觉设定、分镜或提示词任一
阶段直接进入都合法，不为补齐名义流水线伪造上游。

单集创作主链不落盘 JSON/JSONL、索引、指纹、覆盖表、QA 报告、审核表、交接胶囊或恢复状态。
需要 ID 时写进 Markdown 标题；结构检查和批次状态留在本轮上下文，不成为第六份创作文档。建议
写法见 [五份创作文档](creator-documents.md)。

长篇原著拆解或多集材料识别可以在 `项目开发/` 使用机器索引；它们是用户点名时才建立的可选分析
工作区，不是单集创作真相。其存在不会改变 `剧集/<EP>/` 的五文档布局，也不能要求单集 owner
补造并行结构化产物。

创作者说明跟随项目语言。图片、关键帧和视频的可复制正文跟随 `prompt_language`；没有
`short-drama.json` 时默认使用 `en`，同一任务保持一致。两种语言互相独立，不能用一个推断另一个。

## 请求范围

用户点名的范围就是本轮范围。“写完这一集”完成整集；“从剧本做到视频提示词”依次完成所点名
阶段。场次、资产组和镜头组只是内部上下文批次，通过后自动继续，不逐批交还控制权，也不为每个
中间文件另开接受、审查或 QA 回合。

只在三处停下：

1. 点名范围已经完成；
2. 缺失事实形成会显著改变剧情或视觉方向的真实创作分叉；
3. 下一步会调用外部生产，必须先展示精确 job 并取得显式确认。

结构检查服务于发现错误，不是创作门禁。能在当前文档直接修正的问题直接修正；审查、归档和媒体
生产只有用户点名时开始。安装 selftest、全量 QA 和 demo 验证属于技能维护，不属于普通创作请求。

### 完整单集快路径

一次请求横跨四个以上 owner 时，不要因为提示中自然出现“人物、道具、对白、镜头、声音”等常规
创作元素，就预读每个 owner 的全部 craft references。先完整读取路由 skill、各 owner 的 `SKILL.md`
与本文件直接指向的 [五份创作文档](creator-documents.md)，按上游到下游完成第一稿；只有遇到一个
具体、尚未解决的创作判断时，才读取对此判断最直接的一份 reference。每次读取后回到当前文档继续
创作，不为“可能有用”继续扩展参考链。结构校验报错先按诊断修改当前字段；只有诊断无法说明修订
结果时才查校验器或更多参考资料。

### 成稿即闭环

完整单集不要先写完五份文档、最后才做一轮重型 QA。每写完一个 `SHOT-...` 与对应
`MOTION-...`，就在当前上下文用一行短链反查并直接修正，不落盘检查表：

```text
剧本这一拍 -> 镜头起点 -> 冻结帧 -> 按时长排列的动作/对白 -> 镜头终点 -> 下一镜起点
```

这行短链同时回答六个问题：

1. 剧本里的动作、声音、因果反应和回环是否被保留，顺序有没有被下游改写；
2. 冻结帧是否逐物等于起点，双手、持物、门/抽屉、灯、限制动作空间的持续关系和延迟揭示有没有提前变化；
3. 摄影机所在侧是否真的看得到被要求可读的正反面；固定在取景范围内的资产若不入画，是否明确
   被裁切或遮挡；
4. 有序动作是否始终服从已确认的持续关系；逐字对白和至少一次稳定可读停留是否装得进时长，而不是
   靠整体加速；同轨音频是否把口语语言、全部允许发声及事件外底声/静默写完整；
5. 精确文字、钟表或屏幕内容是否有真实输入或明确后期文字层承载；不能把自由生成当可靠字形；
6. 终点是否无跳变承接下一镜起点，人物位置、双手、持物、文字面和光态是否逐项一致。

这是一条成稿时的内联思考，不要求每镜单独保存、单独调用工具或把累计全文重复输出；可以在一次
整体写入前按镜头顺序走完，只有发现问题时改当前段落。

发现问题就在拥有该事实的文档修正，再继续下一镜；不要建立 QA 文档、覆盖表、哈希或审批状态。
机械校验只补结构错误，不能替代这条逐镜短链。整集结束只再扫一次镜头之间的接缝，不重读全部
craft references。

## 创作质量

简化文件数量不等于降低内容标准。各 owner 按具体问题读取自己的 craft references，检查剧情因果、
人物声音、资产身份、空间连续性、镜头职责、可生成性和提示词边界。规则与路由总表见
[knowhow-index.md](knowhow-index.md)。最终回报只说明已完成范围、关键创作决定、真实未决问题和可选
下一步，不汇报内部流水线噪音。

## 跨文档视觉依赖闭环

图片提示词与分镜可以并行，但并行不等于永不对账。一次请求覆盖视觉设定、图片提示词、分镜或视频
提示词中的两个以上阶段时，在点名范围结束前按当前文件重新对齐一次：

1. 《视觉设定.md》每个人物、地点、道具有唯一执行锚点；
2. 每个 `SHOT-...` 的「可见资产」完整，图片提示词项与文字视觉依据恰好补齐这些资产；
3. 分镜拥有的静态视觉锚点逐字进入冻结关键帧和对应 `MOTION-...`；
4. 不论是否有真实输入图，运动正文都在每项资产第一次入画前带上最小执行锚点；真实图片只补充其声明控制的内容；
5. 图片生成成功只产生一个媒体文件，不自动成为下游输入。创作者要求使用它时，storyboard owner
   把实际项目相对路径写成 `REF-...`，video owner 同步生成方式与正文，再重新预览生产任务。

生成顺序不能改变这五条：先分镜后图片提示词，要回填新条目映射；先视频后改分镜，要刷新运动正文；
删除或改名任何视觉项，都要清掉悬空引用。只改一个 owner 的请求不越权修改其他文件，但必须点名已受
影响文档；横跨这些 owner 的请求直接在同一轮完成对账，不把显然可修的缺口留给创作者发现。

## 生产边界

图片、视频、TTS 和音乐生产仍遵守 `preview -> explicit confirm -> run`。生产工具可以在隐藏运行目录
保存 job、确认和审计记录；这些是付费/外部副作用的必要边界，不要求模型把创作内容再抄成长期
JSON/JSONL。job 必须把拥有当前提示词的 Markdown 写入 `source`，输出写到
`剧集/<EP>/制作成果/`；任何提示词、参数、输入或输出路径变化都需要重新预览和确认。
